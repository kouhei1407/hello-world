# 第1,2回
&emsp;ソフトウェア工学とは，ソフトウェアの開発，運用，メンテナンスに対するシステマティックで規律ある，定量化できるアプローチの適用，すなわちソフトウェアに対するエンジニアリングの適用である．ソフトウェアなしで社会が回らないこと，IT人材の不足，ライフラインやインフラとしてのソフトウェアが増加していることなどから，ソフトウェア工学が重要となっている．<br>&emsp;ソフトウェアとは，情報を扱うプロダクトそのものであり，プロダクトを提供する手段である．ハードウェアと異なり劣化しないが，悪化はする．新しいニーズを満たすよう適用したり，より近代的なシステムと相互運用するため拡張したりする必要があるといった特徴がある．

# 第3回
&emsp;ソフトウェアには，誕生，開発・運用，廃止というソフトウェアライフサイクルがある．ニーズの発生によってソフトウェアの企画，計画が行われ，要件定義が行われる．要件定義とは，実現する機能としない機能を明確にすることであり，最初に行う計画に基づいて行われる．これにより，関係者内でのスコープの共有やプロジェクト内容の明文化などができる．要件定義書を基に設計書が作成され，コーディングのための仕様書にする．仕様書に従い制作を行い，テストやデバッグを経て，リリースされる．その後は，稼働時の運用・保守が主となり，最終的にはサービスの廃止や新規ソフトウェアへリニューアルするなどしてソフトウェアの廃止が行われる．

# 第4回
&emsp;プロジェクトとは，有期性や独自性を持つ仕事の事である．プロジェクトを進めるにあたり，バックキャスティングという思考法があり，これには目標設定を明確にする必要がある．ソフトウェア分析は物量に関するものや実行性能に関するものなど様々ある．また，ソフトウェア評価の基準や方法もいくつも存在し，コードの物量やファンクションポイント法，使い勝手などから評価することができる．<br>&emsp;ソフトウェアの開発プロセスは，ソフトウェアの目的や特徴によって適当に選択する必要があり，代表的な手法としてウォーターフォール型やスパイラルモデル，アジャイルなどが挙げられる．これらの開発手法は一長一短であり，ハイブリッド型も多い．

# 第5,6回
&emsp;Work Breakdown Structureとは，プロジェクト目標を達成し，必要な要素成果物を生成するため，プロジェクトチームが実行する作業を，要素成果物を主体に階層的に分解したものである．プロジェクトを細かな作業に分解した構成図であるため，WBSと呼ばれている．WBSの作成では，必要な作業を細かく分解し，作業順に並べる必要があるが，この作業を細かく分解することが難しく，プロジェクト全体を正確に把握する必要がある．WBSを作成するメリットとしてはスコープが明確になることや，やるべき作業を洗い出せること，全体管理と作業計画が明確化されること，実施時はWBSに則って実行できることなどがある．

# 第7回
&emsp;コードは大抵書くことよりも読まれることの方が多く，そのためソフトウェア開発において他人や未来の自分が読みやすいよう可読性の高いコードを描くことが必須である．そのためにはコーディングにおける統一されたルールが必要となる．<br>&emsp;コーディング規則は種々存在し，PythonではPEP8などがある．規則にはコードのレイアウトやスペース，改行，命名規則などのルールが細かく設定されている．そのほかにも，UTF-8以外のエンコーディングは極力行わないことや，ASCII文字以外の使用を極力避けるなどといったルールもある．<br>&emsp;これらの規則を遵守することは重要であるが，プロジェクト内の一貫性を保つことも重要である．

# 第8回
&emsp;バージョン管理では，ファイルを誰が，いつ，どのように変更したかを管理する．これらが管理されていることで，多数のメンバーとも共同で開発を進めることができる．集中管理型と分散管理型があり，前者にSubversion，後者にgitなどがある．<br>&emsp;集中管理型はリモートレポジトリのみがバージョン管理を行い，同時編集でコンフリクトが発生しやすいことや同期に時間が掛かることなどがデメリットである．対して，分散管理型はリモートレポジトリへのアクセス頻度が低く，障害に頑健である．<br>&emsp;gitとは，分散管理型のバージョン管理システムで，変更履歴が残る，変更箇所に戻れる，他人と共同編集できるなどの特徴を持っている．

# 第9,10,11回
&emsp;githubとは，リモートレポジトリホスティングサービスの一つで，オープンソースソフトウェアの主要なポータルサイトである．gitではブランチによって作業を枝分かれさせることができる．<br>&emsp;gitには推奨される運用ルールが存在し，gitフローやgithubフローと呼ばれる．githubフローでは，具体的な変更はローカルのブランチで行い，mainブランチでpushやpullを用いて開発部分をmainブランチにマージする．<br>&emsp;レポジトリには，ローカルレポジトリとリモートレポジトリがあり，ローカルレポジトリは個々のプロジェクト実行環境，リモートレポジトリはgithubなどの共有の管理場所のことを指す．

# 第12,13回
&emsp;CIとはコード変更を共有リポジトリに頻繁に統合するプロセスで，自動テストとビルドを定期的に実行することでバグの早期発見と修正を可能とする．<br>&emsp;CDとはコード変更をテスト環境や本番環境に自動的にデプロイするプロセスで，自動デプロイメントを組み込むことで手動操作でのデプロイを不必要とすることができる．CDとCIを用いることでGithubにあるリモートレポジトリの内容をウェブページとして公開できる．HPの更改はCIやCDによって自動化する．またJekyllを使用することでmarkdownファイルを自動でhtml化できるため，開発者はmarkdownファイルを作成することでウェブページを作成できる．
